# 28 — Durable coordinator store

W01.1 / [#14](https://github.com/alex-engvall/labstride/issues/14) introduces the first application persistence slice. It uses TypeScript, Node's built-in SQLite and a local durable state directory. It does not dispatch operations, authenticate provider inputs, claim effects or run a session adapter. Those boundaries remain W01.2–W01.4 and W02–W06 work.

## Entry points and trust

`startCoordinator(dataDir)` opens the actual store, migrates it and returns the coordinator, store and recovered snapshot. The core depends on the `StateStore`, `Clock` and `IdentityProvider` ports. Only the composition root imports SQLite; core has no filesystem/provider dependency. Optional clock/identity implementations belong to the trusted embedding application, never issue payloads or configuration URLs.

Run the bounded bootstrap inspector with `node apps/coordinator/main.ts /srv/labstride-state`. Supply an installation-owned absolute local path. The process prints a versioned JSON snapshot and exits without executing effects. This is not `labstride serve`, the authenticated operator CLI or an installed background service. Errors print a stable redacted code and return exit status 1. Snapshots contain operational metadata; callers must protect access.

The public core works without an agent, hooks, deployment credentials or a private package. It stores opaque session handles; it neither creates a session backend nor substitutes another client. Input adapters must authenticate and authorize requests before invoking the store and must supply credential references rather than secrets. Persisting an evidence reference records the trusted caller's observation, not independent proof of its truth.

## Persistence API

`commit(changes, context)` atomically applies up to 64 changes. A change contains a versioned lifecycle record, `expectedRevision` (null for creation) and an optional recovery flag. The context requires actor identity, a bounded reason and evidence references. Every successful change appends an audit snapshot in the same transaction. Runtime schemas and a 256 KiB per-record/audit limit apply before persistence. Payload validation never retrieves remote schemas.

`get(kind, id)` reads a validated record. `snapshot()` reads independent records in one database snapshot, keeping original identifiers. `history(runId)` reads related records and append-only audit under one read transaction. `close()` closes the database; restart reopens the same file rather than rebuilding identities from provider history.

The new [record](../schemas/lifecycle-record.schema.json) and [audit](../schemas/lifecycle-audit.schema.json) schemas version persisted data independently from the existing external v1 operation/session contracts. Generated TypeScript participates in the repository's type/drift checks. Ajv `8.20.0` and ajv-formats `3.0.1` are now pinned runtime dependencies (MIT); `@types/node` `24.19.2` and its locked undici-types dependency are development-only MIT dependencies. The [W04.1 broker](38-workflow-broker.md) also uses existing pinned MIT-licensed jose 6.2.13 as a runtime dependency. Packaging and clean-install qualification remain W07.

## Identity, transitions and recovery

Installation configuration revision, request provider/issue/generation, run repository/configuration, workspace ownership/locator/branch, operation request, deployment source/target, session enrollment and projection binding are stable. New configuration revisions use new installation snapshot identities. SQLite enforces request-generation uniqueness, one run per request, one live workspace per run, operation/intent linkage, session-provider/handle uniqueness and cross-run foreign keys. W01.3 now enforces one live run per canonical issue across generations/configuration snapshots and scheduling limits; see its runtime contract below.

New records start at revision 1 and updates compare the previous revision in a write transaction. Lifecycle transitions follow the explicit tables in core; unlisted transitions fail. A run's `paused` flag is independent of its current phase and checkpoint. W01.3 now applies the persisted pause flag through explicit audited scheduling controls; see below. Session state changes never change the run's state or grant plan approval.

Failed runs, errored workspaces and unknown outcomes require an explicit recovery change with evidence to change phase. Terminal operation/deployment/session outcomes and completed/cancelled runs cannot be rewritten through lifecycle transitions. A crossed operation effect boundary cannot be reset. A new operation and its original outbox descriptor must commit together; the store supplies no executor permission.

Recovery distinguishes `pendingIntents` for prepared, not-crossed operations from `reconciliationRequired` operations that are claimed, running or uncertain. All original descriptors remain in `records`, including those for terminal operations. Neither recovery list authorizes dispatch, proves a remote process stopped or supplies exactly-once execution. W01.2 owns claims, dispatch/retry timing and actual reconciliation.

## Resource retention and local path boundaries

Schema v2 adds an immutable resource inventory and evidence records for PR, merge, deployment, cleanup and corrections. Resources bind their creating operation, workspace, run and ownership reference. Evidence binds an operation/workspace/run, source and target identity, observed outcome and external reference. A verified cleanup record requires a tombstone reference. A correction appends another record referencing existing same-workspace evidence; it never rewrites the original. SQLite foreign keys and immutable-record triggers preserve those links after a workspace is marked deleted. There is no store method that deletes workspace metadata or resource history.

`startCoordinator(dataDir, { localWorkspaceRoots })` checks configured local roots before creating the state directory. The store resolves existing parents of paths that do not yet exist. At registration, update and every restart, recorded local workspace paths must remain disjoint from the state directory in both directions. Canonical aliases are resolved; dangling links and overlapping paths are rejected. Existing database, WAL, SHM and rollback-journal entries must be ordinary single-link files. Linked/unmanaged entries are preserved and rejected before SQLite opens them.

These checks assume an installation-owned local filesystem without an adversary replacing paths concurrently. They do not provide the target-side, race-resistant deletion/ownership/quiescence helper required in W03/W05. Opaque remote locators are metadata, not permission to resolve or delete a local path. The core performs no workspace deletion or hidden cleanup timer. W06.3 adds [explicit diagnostic compaction](16-operations-and-cli.md#explicit-diagnostic-retention) with transactionally guarded eligibility; lifecycle/resource/evidence history remains immutable.

The [retention evidence](evidence/W01.1-retention-2026-10-21.md) exercises real removal of a test-created directory, retaining the run/resource/merge/deployment/cleanup graph and a separate directory. It does not pass the full target tombstone/lost-workflow-acknowledgement case AC20.

## SQLite and upgrade limits

The store enables foreign keys, WAL and `synchronous=FULL`, with a 5-second lock wait. Writes use `BEGIN IMMEDIATE`, bound values and atomic audit insertion. No network work is performed in transactions. A conflicting revision, reference or uniqueness constraint rolls the whole batch back. Audit update/delete triggers reject mutation. This is append-only application history, not tamper-proof storage against a database administrator.

Schema migrations have ordered versions and SHA-256 checksums. Migration DDL and version updates commit together. Schema v1 upgrades to v2 without changing existing identifiers or audit records. An unknown newer version, missing migration ledger or changed applied migration is rejected. A failed migration leaves previous schema/data intact. There are no automatic down migrations, database resets or background retention deletions. Migration 21 narrowly permits explicit eligible diagnostic compaction and retains other immutability protections. The v1 executable rejects a v2 store: downgrade requires a forward fix or a deliberately restored compatible backup, followed by reconciliation before effects. Before an operator-led upgrade, pause effects and take a consistent SQLite backup; WAL-aware backup/restore qualification belongs to W06. Restoring an older file cannot authorize replay of external effects.

Tested runtime: Linux x86_64, Node `24.22.0`, linked SQLite `3.53.4`. Tests prove process-crash recovery, not power-loss durability, network filesystem support or multi-coordinator operation. See the [evidence and remaining acceptance boundaries](evidence/W01.1-lifecycles-2026-10-21.md).

## W01.2 durable inbox and scheduling

The application bootstrap now composes `ExecutionStore`, retaining the inspector's no-effect behavior. `receive` validates a bounded versioned inbox envelope and atomically commits the normalized event and optional compare-and-set checkpoint before returning its stable ID. Deduplication is scoped by installation, provider, stream and external delivery identity. Conflicting content fails; identical replay preserves the ID. Source versions are opaque.

`pendingEvents` and `scheduleStart` provide the trusted adapter boundary. Only an authenticated, authorized policy adapter may construct a start plan and audit context. Event origin and actor fields alone do not establish authorization. Scheduling checks event/actor/installation/issue/generation correlation, canonical request digest, references and configuration revision; the original request/run/workspace/operation/outbox, queued projections and event completion commit together. Repeated authorized starts return the original run. Ordinary observations cannot call this path as start events.

Schema v3 adds inbox/checkpoints, immutable execution bindings and separate delivery state. Existing v1/v2 records retain identity and audit and acquire no execution binding or permission. Generic lifecycle writes cannot mutate an execution-bound operation, even through the base store. Dispatch/claim/reconciliation methods are the next W01.2 slice. This slice neither performs external effects nor passes AC01 or integrated AC02/AC35/AC36.

## W01.2 claims and effect recovery

`createWorker` is an explicitly composed bounded tick, with a trusted exact action ID/version registry. It never imports code named by an event, starts from the inspector, or requires private packages. Adapter validation receives a copy; dispatch uses the stored request. A registered action must validate its own pinned inputs and configuration. Authentication, production extension loading and remote workflow authorization remain adapter/broker work.

`claim` atomically checks the current generation, run pause/terminal state, request deadline/digest and execution binding; records an executor/attempt, resource lock and monotonic fence; and moves delivery to reconciliation. Duplicate same-executor/attempt claims return the original claim. `beginEffect` consumes that claim once and commits the crossed boundary before adapter invocation. Lease expiry never releases locks. Generic lifecycle mutation cannot bypass this boundary. These are local coordination fences; remote fencing requires target support.

The worker re-observes claimed/running/unknown operations after restart. No uncertain effect is automatically replayed. An absent resource is still unknown. Only known pre-effect transient validation errors and read-only observations receive bounded persisted retry timing (default five attempts, exponential 1-second base, 60-second cap, half-to-full jitter). Exhaustion blocks delivery; `resumeObservation` requires evidence and resumes reads only. Errors after invocation always preserve uncertainty.

Bound direct results carry operation ID, request digest, handle, resources and evidence without invented workflow executor identity. Terminal result, retained action-produced resource references, lifecycle audit and optional follow-up projections commit together. Identical results are idempotent. Conflicting results append evidence and hold the resource; original terminal history remains unchanged. Handles cannot be silently replaced. Resource `providerId` identifies the producing action; no external service identity is inferred.

Schema v4 appends claims/fences, immutable terminal results and execution history, resource conflict holds and restore control. `enterRestore` must run before starting workers on an explicitly restored database; it pauses effects and requires observation of every recorded operation, including already terminal operations. `resumeAfterRestore` requires evidence and all checks resolved. Legacy unbound operations remain held and require later operator/adapter enrollment; arbitrary replacement of the database and effects absent from that backup are not automatically discovered. Full backup tooling and target inventory reconciliation remain W06.

The [effect evidence](evidence/W01.2-effects-2026-10-21.md) passes AC01 with an actual killed coordinator and a separate durable effect receiver. It is not a live SSH/deploy/client qualification or power-loss/multi-coordinator support claim.

## W01.2 observations, projections and explicit runtime composition

`ObservationStore` completes the store composition. `startExecution` combines the action and observation workers through trusted adapter maps. Its optional restore context is committed before either worker can execute. Restore increments an observation epoch: delayed receipts and reads begun before that epoch cannot satisfy the fresh reconciliation gate. `tick` performs bounded work; the embedding service owns invocation timing. `close` waits for its current tick. There is no new background service, public listener, code loader or implicit adapter installation. `startCoordinator` remains the effect-free inspector.

`receiveHook(enrollmentId, observation)` validates the normalized hook and enrolled provider/run/generation/workspace/session, commits it into the inbox with a durable session-read wakeup, then returns the existing versioned acknowledgement. Hooks are advisory, including turn-stop/interruption. They never change run state or grant a new effect. Opaque session/turn handles now use bounded strings in the hook schema, matching lifecycle enrollment; they are never paths. Initial live hook ingestion remains disabled because no transport or provider translator is installed.

The observation worker re-reads enrolled sessions at startup and every configured interval (default 60 seconds), including sessions enrolled later without a hook. A hook arriving during a read changes the queue revision; a human update changes the session revision. Either rejects the stale response. Observed human activity never regresses and retains human ownership. Session state, the backend observation, processed hook records and optional progress projections commit together. Source versions are opaque and arrival timestamps cannot order provider history. Read exhaustion remains blocked across restart; explicit evidence-backed `resumeSessionObservation` resumes observation, not continuation.

Projection descriptors remain immutable. Their separate delivery and attempt records preserve write-token identity across crashes. Before every write the worker checks the current request generation, provider identity and field fingerprint. The adapter must explicitly provide atomic generation-and-version preconditions; without them delivery blocks as unsupported. These guarantees are exercised by the synthetic provider, not asserted for GitHub. W02 must qualify its actual provider support or keep unsafe writes blocked.

An independent read confirms the current value and applied write token. Changed human/provider state causes conflict; older-generation work is superseded. Missing acknowledgement with an unchanged field is still uncertain and is never blindly resent. Only a trusted `PreEffectTransient` rejection from the write itself proves that no write was submitted; it can be retried after fresh observation. A read failure after a successful write cannot be reclassified this way. No claim of general exactly-once delivery is made.

Schema v5 adds session-poll and projection-attempt metadata, preserving earlier payloads and digest compatibility. Local acquisition timestamps on duplicate deliveries retain the first stored timestamp rather than altering source identity. Legacy projection descriptors receive no automatic execution permission. Restore blocks new projection effects while observations continue. Resource-conflict holds and unresolved restored operations require later operator tooling; no timer releases them.

[Observation and closeout evidence](evidence/W01.2-observations-2026-10-21.md) distinguishes the completed local implementation from live AC02/AC09/AC21/AC35/AC36 gates.

## W01.3 admission, controls and automation safety

The [lifecycle specification](07-lifecycle-and-recovery.md) defines the implemented trusted APIs for scheduling policy, follow-up operations, pause/resume/cancel/takeover, budget renewal and diagnostics. Migrations v6–v8 append durable run reservations, class assignments, control identities, stop submissions and budget/session guard metadata. All old operation digests, records and audit survive. Legacy conflicting starts remain inspectable and block new effects until explicitly resolved; no arbitrary survivor or expiry unlock is chosen.

`startExecution.tick` pumps bounded action/control jobs alongside the observation lane and returns without waiting for external effects. `drain` waits for current work; `close` disables runtime ticks, drains workers and closes SQLite. A hung adapter can delay draining; adapter transport timeouts and installed-service shutdown policy remain integration responsibilities. Closing the process never proves a target stopped. The bootstrap inspector still initiates no effects, and no new service, listener or package loader is installed.

Local [capacity evidence](evidence/W01.3-capacity-2026-10-21.md), [control evidence](evidence/W01.3-controls-2026-10-21.md) and [automation evidence](evidence/W01.3-automation-2026-10-21.md) cover the scoped implementation. LS-CORE-005/007 are implemented, not verified; complete AC08/AC24/AC31/AC36 integration remains with #17/#22/W06 and the other named owners. Pause and take a consistent backup before upgrade. There is no automatic down migration or permission to replay effects after restoring older state.

## Bounded publication read recovery

The [self-build publication correction](evidence/W04-W06-shallow-publication-2026-10-24.md) records remote intent only after local preparation and rechecks. Exact independent remote observations may complete the original acknowledgement with an evidence log entry. Fresh bound `accepted` observations reset consecutive read failures and clear stale delivery errors; unknown or failed observations do not. This does not remove uncertain managed effects, cancellation records or replay authority checks.

The [bounded report observation evidence](evidence/W04-W06-bounded-report-observation-2026-10-24.md) records a live post-publication read failure caused by a transcript exceeding the native RPC bound. Journaled delivery uses repeated latest-turn metadata checks instead; original uncertain effects and the blocked observation remain distinct. Resume only supported read observation after an approved correction, without resetting managed intents.
