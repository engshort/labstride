# 37 — Local issue-to-review installation

This bounded W04/W06 implementation composes existing W01/W02/W03 components. It is an opt-in Linux/Node 24.22.0 pilot, not a complete W04/W06/W07 release. See [ADR-007](adr/0007-checked-codex-delivery.md) for the accepted weaker delivery model and [evidence](evidence/W04-W06-local-self-build-2026-10-24.md) for verification limits.

## Observable workflow

Bind six native organization issue fields by stable provider IDs: request/progress, AI mode, model, reasoning, registered session and source path. Option IDs are discovered and validated; names and catalogs are installation configuration. No Project membership is required. The [operational template](../examples/operational-installation.json) is disabled and uses synthetic identities. Startup defaults are explicit option-ID mappings; the selected local profile uses Plan mode, GPT-6.1 Sol and Medium. An unsupported explicit choice blocks without fallback. Fill a default only while the field remains absent, through the checked projection writer.

Initial import is inert. A new independently attributed, authorized transition to Approved creates a run and isolated branch/checkout. Frozen configuration/policy and transactional workflow steps bind subsequent coding to that verified checkout. Path comes from its committed receipt and protected root mapping. The session field comes from the successfully created and registered main session, never issue text.

Plan mode observes Planning and then Waiting for accept; the user approves implementation by continuing in the same session. Direct mode observes Working. No agent leaves the ready checkout available. The versioned startup selection is committed before any native creation intent and retained across recovery. Later AI field edits cannot replace an uncertain start with No agent or change its original model. AI fields are startup settings and do not override later app settings. The coordinator never answers app questions or approvals. The qualified bridge starts legacy-history threads and verifies the latest native turn using bounded metadata reads. Journaled reports do not require transcript hydration; history-only compatibility recovery still requires an explicitly full snapshot of the same completed turn. Fresh empty-session delivery additionally requires the uninterrupted creation/activity witness described in [ADR-007](adr/0007-checked-codex-delivery.md); an unavailable method or a reconnect never grants an empty-history assumption.

A versioned native result report identifies the completed turn and exact commit. The bridge journals validated native tool requests before acknowledging success, because legacy history may omit the tool item. Publication uses a journaled report only when its original turn is the latest completed native turn, confirmed by a second bounded summary read. It never reloads the transcript to authenticate a journaled receipt. Once journaled delivery is established for the same receipt/session binding, a later conversation without a report returns normal waiting without loading its transcript or reusing an earlier report. Sessions without any bound journaled report retain the bounded, explicitly full history-only compatibility path; missing, oversized or conflicting legacy evidence cannot authorize publication. Publication verifies a clean registered branch, ancestry, nonempty changes, DCO and unchanged CI workflow definitions. Bundle preparation uses only the already-registered source SHA as a shallow-history boundary, so a depth-one checkout need not supply earlier history. Local import/validation and the final native-turn check complete before a remote push intent is recorded. Git transfer crosses the coding bridge as a bounded bundle; installation credentials are available only in the coordinator's publication process. Code hooks and source commands never execute with those credentials. The configured PR is reused for later work and human title/body edits are preserved. A lost push acknowledgement can be adopted only from the exact repository/branch/head ref. A lost PR acknowledgement can be adopted only from one open PR with the matching run marker, source repository, branch, base and head SHA. Absent or conflicting evidence never permits another mutation for that intent.

Missing, pending, failed or skipped checks in required workflow suites prevent readiness. Match every suite and check to the current head; optional deployment jobs in other suites do not become required when deployment is disabled. Only successful configured repository workflows, check runs and statuses on the current PR head permit Waiting for review. Keep observing the same session for follow-up commits. Merged requires an observed GitHub merge with the recorded head. Deploy and automatic merge are disabled. Repository-owned CI must already exist on the base branch before a real self-build can pass; merging the implementation PR is an operator prerequisite.

## CLI and service

The executable entry point is `node apps/cli/main.ts`; the administrative bootstrap installs a `labstride` launcher for root to run it as the coordinator identity. Commands return JSON with safe codes and exit status; `--human` provides diagnostic/inspection formatting. The [public prepared-host profile](40-public-installation.md) adds a separate v2 configuration without native fields or a bridge.

| Command | Implemented behavior |
| --- | --- |
| `labstride version --json` | Report packaged source revision (or explicit development/null identity) and running Node version without operational access |
| `labstride init DESTINATION` | Create a new disabled template, refusing to overwrite an existing file |
| `labstride config validate --config FILE` | Compile exact schemas, extension pins, field bindings and qualified history using the selected credential |
| `labstride doctor --config FILE` | Check compiled profile, dedicated installation/repository scope, Codex catalog/defaults, SSH/helper root mapping and SQLite integrity/version |
| `labstride serve --config FILE` | Run bounded polling and workers under a kernel process lock; drain on shutdown |
| `labstride runs list` / `show RUN` | Show controls, operation outcomes, frozen startup selection, session and field/summary conflicts |
| `labstride runs pause RUN` / `resume RUN` / `cancel RUN` | Submit local operator controls with revision checks; an interrupt acknowledgement is not confirmed cancellation |
| `labstride runs reconcile RUN` | Resume blocked read observation; retain conflicts and unknown effects |
| `labstride provider rebaseline ITEM_ID` | With the coordinator stopped, explicitly establish a new inert baseline for an item with no prior request; preserve history and require a later fresh authorized transition |
| `labstride backup DESTINATION` | Create a consistent SQLite backup without replacing an existing destination |

The outbound issue/PR chain explicitly permits `broker: {"enabled": false}`. Broker-dependent action/connector profiles remain rejected without their required configuration; workflow claims/deployment are not implemented by disabling the broker. The loop uses existing bounded provider retry/budget logic. A known accepted action waiting for a person/CI polls without exhausting a transient-failure retry budget. A fresh bound running acknowledgement resets consecutive read failures and clears stale delivery errors; an unknown result does not. Successful self-build observation/review clears its recovered workflow diagnostic, without deleting uncertain mutation records.

Both run views retain the `startup` array independently of `session`: a lost native creation reply can leave a frozen Plan/model/reasoning choice with no registered session. The view uses validated saved startup records, never current field values or arbitrary native intent payloads. Reopened inspection preserves those choices without issuing another session start.

Native field writes are serialized per installed run, with a fresh issue observation between outputs. Summaries wait for pending field writes so their own comments do not invalidate those fingerprints. Remote/manual races remain possible. A conflict preserves the manual value and is visible in CLI and the managed issue summary; it creates no new progress option. A manually edited summary is not replaced. Unknown creates/updates are not blindly retried.

## Reviewed administrative bootstrap

1. Commit the reviewed source and run `python3 scripts/package_local.py NEW_BUNDLE_DIRECTORY`. It packages the exact source revision, existing locked dependencies, Node binary/license and hashed extension artifacts. It downloads nothing and refuses a dirty worktree. The administrative installer also supports `--stage-only` to verify/copy a release without changing service configuration; this is not an automatic upgrade command. Record the manifest SHA-256 from its JSON output.
2. Prepare private installation configuration from the template. Independently verify a dedicated GitHub App installation on the organization with only the intended repository selected. Required grants: Contents/Issues/Pull requests write; Actions/Checks/Commit statuses read; organization Issue Fields read. No broad CLI credential is a substitute. An installation token has no human GraphQL repository role; the native adapter verifies `viewerCanSetFields` on the independently enrolled issue and rechecks it on every write.
3. Review `scripts/install_local.py`; run its `--dry-run` first, then run it administratively with `--bundle`, `--manifest-sha256`, `--configuration`, `--coding-user` and `--backend-socket`. It preserves existing/mismatched paths, installs root-owned immutable release files, creates separate coordinator/helper identities, copies protected credentials, enrolls a forced-command SSH helper against the local trusted host key and writes disabled systemd units. For App keys it retains the original file but withdraws coding-user read access to the same privileged key. No temporary administrator key is a runtime dependency.
4. The bootstrap layout is `/opt/labstride/releases/REVISION`, `/etc/labstride`, `/var/lib/labstride` and `/srv/labstride/workspaces`. Runtime field mappings, repository/target identities, roots and model catalogs stay in configuration. The bridge runs as the existing coding user against the existing daemon. Named UID ACLs grant checkout access to that already running daemon without restarting it; protected receipt wrappers and service state remain outside its write authority.
5. Initialize disabled SQLite with `labstride state init`; start only the bridge for preflight. Run config validation and doctor. Perform actual negative reads/writes as the coding UID: coordinator state, configuration, credentials, helper policy/registry and release files must remain inaccessible for mutation, and credentials/state inaccessible for reading. The workspace probe requests the versioned `workspace.root-map.v1` proof over enrolled SSH. The helper verifies the full root identity including its target mount ID; the coordinator checks that proof against protected mapping and its own view of the same device/inode/UID. This preserves systemd mount sandboxing without treating its different local mount ID as a target mismatch. Verify two registered checkouts allow coding writes but protect their ownership markers and parent roots. Check duplicate service exclusion and orderly shutdown/restart.
6. Take a consistent backup before activation. Administratively set only the reviewed installation's `configuration.enabled` to true, then enable/start the coordinator and bridge. Observe the inert first import before creating a new Approved transition. Keep historical pilot resources untouched.

The installer leaves both services stopped and the listener disabled. Installation identity, private paths, account data, temporary keys and tokens belong in private operator records, not this repository.

## Report journal and existing installations

The bridge policy supports an optional absolute `reportDirectory` naming an existing, protected directory outside the source checkout. It contains a private `managed-reports/reports.sqlite` journal (schema version 1); the journal directory and files must belong to the bridge identity with private permissions. Native report payloads remain untrusted data and do not carry installation credentials or publication authority. Report commits precede successful native tool responses. Duplicate native call IDs with identical payloads are idempotent; conflicting report payloads in the same completed turn block publication.

Fresh administrative bootstrap provisions a private bridge-owned report directory under its managed state root and selects it through `reportDirectory`. Existing configurations fall back to `stateDirectory` for compatibility. If that path is a runtime directory under `/run`, the journal survives a process reopening it but can disappear when the service manager removes the directory or the host reboots. An existing installation needs a separately reviewed persistent directory and policy update to retain reports across those events. This code change performs no live installation update, migration, service restart or old-report import. Keep the journal when rolling back; removing it loses evidence and never authorizes a replay.

A report acknowledged by an older bridge can be absent from both history and the new journal. Preserve the original run/workspace/session. After the operator has installed the correction, request a fresh report of the already committed result in that same session. Do not start another task, resend the initial instruction, bypass current-turn checks or manually insert a receipt. The [report handoff evidence](evidence/W04-W06-report-journal-2026-10-24.md) separates the actual native finding from controlled publication tests and the remaining installed recovery gate.

## Verification and recovery

Require two independent issues/workspaces, duplicate Approved delivery, inert import, unauthorized actors, defaults, unsupported combinations and manual projection conflicts. Kill real processes/drop responses around checkout, thread start and publication; preserve unknowns. Complete native planning, the operator's actual approval, implementation, reconnect and a real PR with current-head CI. Exercise simultaneous manual turn start and retain uncertainty. A local fake provider is useful regression evidence but cannot pass those live gates.

The self-build canary is a new issue requesting `labstride version --json` with installed revision and Node version. It must produce actual code in the same session, correct fields, green checks and a reviewable PR. Issue #70 implements that bounded command with [documented release/development semantics](16-operations-and-cli.md). Its [local command evidence](evidence/W06-version-canary-2026-10-24.md) does not by itself establish native result publication, merged CI, or installed-service qualification. The earlier #68 unknown run, workspace and session remain preserved; this independent canary grants no replay authority.

Pause new effects before backup/upgrade/restore. Retain the previous release and every pin needed by active runs. SQLite backup is implemented; automated restore/upgrade commands are not. Recovery must use the existing restore fencing plus independent reconciliation of external results before resumption. Stop the coordinator before both `recovery begin` and `recovery resume`; both commands require the service lock. The public v2 `serve --reconcile-only` mode is separate from this pilot's runtime qualification. Do not downgrade the database, reset it, remove unknown workspaces or self-upgrade. If live gates fail, keep the coordinator disabled/stopped and preserve state, checkouts and original outcomes for inspection.
