# 32 — GitHub observation and checked projections

W02.3 / [#20](https://github.com/alex-engvall/labstride/issues/20) implements **LS-GH-003/004/005** on the existing configuration, authorization, inbox and projection foundation. [Evidence](evidence/W02.3-reconciliation-2026-10-23.md) distinguishes local process recovery, actual GitHub effects and remaining SSH/session acceptance. These are trusted embedding APIs, not an installed public service or CLI.

## Installation and supported bindings

Construct `GitHubClient` with an installation-owned credential resolver and `GitHubAdapter` with the configured provider ID, effective configuration and independently enrolled history qualifications. The client uses the repository credential reference for native repository fields and the separate Project credential reference for Project fields, item state and actor-bearing history. It never broadens a grant or silently substitutes another identity. The HTTPS GraphQL URL remains configurable; redirects, credential-bearing URLs, oversized responses and partial GraphQL error responses are rejected. No new runtime dependency is added.

Project text, number, date and single-select fields can be read and projected when their actual types/options and `viewerCanUpdate` permit it. Native issue/PR title, body and state are read-only string bindings, qualified against the configured repository ID/name. The separate [native organization issue-field adapter](35-native-issue-fields.md) supports repository-scoped custom fields and independently qualified field-specific history. Other sources/types fail preflight; current-state readability does not imply recoverable transitions. Draft items, inaccessible content and repositories outside the allowlist cannot start work. Item field-value connections exceeding the current 100-value bound fail explicitly rather than turning a truncated page into missing values.

Only an explicitly qualified built-in Status binding advertises `changedTo` history and actor attribution. Its version `1.0` [enrollment](../schemas/github-history-qualification.schema.json) records Project/field/content/event/actor IDs, the independently qualified option ID and the event's recorded status string. Installation code must establish this relationship with a controlled fixture using the selected credential; copying a current value/creator into an enrollment is insufficient. `describeField` re-fetches the configured field and the actual issue/PR timeline event. Unknown/redacted actors, missing events and wrong IDs fail qualification. The enrollment retains the stable option ID through display renames; it is not a remotely supplied permission token. Arbitrary Project-field and draft change history remain unsupported; native organization issue fields use their own explicit qualification.

Compile with this adapter's `describeField`, then activate configuration and publish bounded policy through the W02.2 operator capability. One Status history binding is supported per observed Project. Start conditions spanning multiple independently observed Projects are not qualified by this implementation. Display names are hints; deleted fields/options and type changes block the binding. A `User` actor, webhook signature or `wasAutomated=false` still does not prove a human gesture or approval.

## Polling, bootstrap and admission

`createGitHubWorker(store, { compiled, adapter, buildPlan })` registers streams against the exact active snapshot. `startExecution` accepts this as its optional `github` argument and invokes the worker with its existing observation tick. Its GitHub projection adapter is registered in the single projection map. There is no new hidden timer, network listener or extension installer.

The configured polling interval applies, normally 60 seconds. The production client defaults to 32 requests per tick, a 15-second request timeout, 20 items per enumeration page and 100 timeline events per page. Incomplete enumerations/history retain durable cursors. Completed history scans overlap their last page; stable event IDs deduplicate acquisition without using timestamps, returned list order or `totalCount` as execution identity. Errors, budgets, retry deadlines and exponential backoff with jitter are durable. Retry-After/rate-limit reset observations are bounded and honored; credentials are resolved for each call so rotation does not require copying a secret into state.

Item enumeration and its checkpoint commit together. History pages and their checkpoint commit together. Terminal history/current-state reconciliation records pending candidates separately from admission. Initial import, newly observed membership, removed/re-added membership and an invalid-history-cursor rebuild establish an inert baseline. A full rescan retains all run, operation, session and candidate identities; it cannot import historical starts. A failed Project-list cursor restarts enumeration without advancing an unverified checkpoint.

For a supported field, map historical status strings against both observed option-name revisions and stable option IDs. Ambiguous names, missing history or more than twelve unresolved Status transitions or 4,096 classification steps block classification. Distinct timestamp seconds constrain ordering; tied events require a unique state-linked path between the recorded baseline and refreshed current state. No history list is executed as an instruction stream. Only the last uniquely established current transition becomes a candidate.

GitHub can expose the changed current value before the corresponding timeline event. A missing/ambiguous history result preserves the previous baseline and unconsumed events, records a diagnostic and retries later. It never consumes the transition merely because the current-state read arrived first. A newer candidate supersedes older unadmitted candidates for that membership.

A missing or ambiguous history classification does not stop other items in the same stream. The blocked item retains its diagnostic, baseline and unconsumed events, waits for the next enumeration, and cannot admit an earlier pending candidate while that diagnostic remains. Provider transport, credential, budget and cursor errors retain stream-level backoff. Inspection counts blocked items separately, and Doctor reports them even when the rest of the stream is current.

For an item that has never produced a request, an operator may explicitly run `labstride provider rebaseline ITEM_ID` while the coordinator is stopped. Use the provider's item ID: the issue node ID for native fields, or the Project item/membership ID for the public Project profile. The command takes the service lock, requires local operator authority and the active installation/provider binding, preserves history and all execution records, supersedes only pending candidates for that item, and records an audit entry. Its next observation establishes an inert baseline; a later fresh authorized transition is still required. An item with any earlier request is refused, including completed or uncertain work. This is not automatic history repair or permission to replay an effect.

Candidates bind source repository/revision, actual history actor, snapshot digest, event identities and a transactionally allocated request generation. Re-observe current item identity/fields/source before admission. Changed or unavailable state supersedes the pending candidate. Admission, authorization decision, original run/workspace/operation/outbox and candidate receipt commit atomically through `requestConfiguredStart`. The synchronous actor verifier reads only those independently persisted facts; audit context and incoming event fields cannot manufacture them. Duplicate/concurrent observations retain one generation and graph.

`githubStatus`, `githubItemDiagnostics`, `githubCandidates` and existing configuration receipts expose checkpoint errors, blocked/ambiguous history and original decisions without secret values. Doctor and authenticated remote operator UX remain W06 work.

## Signed webhook transport

`createGitHubWebhook` supplies a standard Request/Response handler for an operator-configured HTTPS route. It bounds raw bytes before parsing, verifies `X-Hub-Signature-256` with constant-time HMAC comparison, and parses JSON only after authentication. It returns 202 only after the delivery ID/digest and wakeup are committed; exact duplicates return the original durable receipt and changed bytes under one ID return 409. Storage failure cannot return accepted. The default body limit is 256 KiB, configurable up to 1 MiB.

Authenticated payload fields are still inert data. A delivery only wakes provider reconciliation and cannot authorize start, completion, approval or a policy change. Personal Projects use outbound polling; this handler does not claim their field changes have organization Project webhook availability. Public ingress provisioning/TLS and real GitHub webhook subscription delivery remain installation qualification work.

## Single writer and checked recovery

`ProjectionAdapter.capabilities` declares version `1.0`, mode `atomic`, `checked` or `unsupported`, and whether durable remote write identity exists. Existing `atomicPrecondition` adapters remain compatible. Atomic generation/version guards and session/turn guards retain their stronger requirements. GitHub declares `checked` and no durable write identity: its mutation has no field-version CAS, and `clientMutationId` is only response correlation.

Projections retain the logical issue/PR `subjectId`. Their optional versioned `providerTarget` pins the exact Project scope and membership resource ID; a removed membership is never silently redirected to a replacement. Run snapshots bind permitted technical field IDs and mapped values. A later configuration revision does not rebind an existing run's projection, including after coordinator restart.

Only observed `run.<state>`, `workspace.<state>` and independently refreshed `session.<state>` facts automatically enqueue configured mappings. Trusted embeddings may explicitly enqueue other verified facts. Hooks cannot directly enqueue an authorized start or set run completion. Progress from the same run/fact/field/value has a stable identity. Only unsent projections without an attempt are coalesced; any started attempt fences later writes to the same provider/subject/field across processes.

The writer refreshes state, records its attempt before mutation, performs another immediate pre-read, verifies the pinned field and current policy/generation, writes only the mapped field and reads back. A successful mutation plus matching readback is durably acknowledged, then independently checked. A proven pre-submission failure may retry. A lost response or process death before acknowledgement remains uncertain even if the field currently matches. It is never retried as a new write; new progress cannot bypass that outstanding attempt.

Observed human/provider changes produce a durable field hold and a visible conflict through `projectionDiagnostics`. An acknowledged write followed by a different version is also a conflict. `clearProjectionConflict` requires operator control authority for configured runs and refuses to release any uncertain attempt. Clearing a resolved hold does not replay the old projection; a fresh reviewed fact/value must be enqueued. Unknown outcomes require independent evidence and reconciliation, not SQL edits or a generic retry button.

**Limit:** pre-read/write/readback is not an atomic transaction with GitHub. An intervening human write can be overwritten without an observable intermediate state. Item timestamps provide conservative fingerprints and may also detect unrelated item changes. A detected conflict is retained and further automatic overwrites stop; no claim of guaranteed preservation, exactly-once remote mutation or remote rollback is made. This checked behavior is the explicitly accepted W02.3 tradeoff, not a weakened session-control guarantee.

## Upgrade and qualification

Migration v12 appends observation streams, membership snapshots, history, generations, candidates and webhook receipts, plus checked-projection attempts and field holds. Migrations v1–v11 and their checksums remain unchanged. Existing atomic attempts default to their original mode; no provider receipt or actor is invented. Pause effects and take a consistent backup before upgrade. There is no automatic down-migration. Restoring an older database requires external-effect reconciliation and the original pinned artifacts/credentials.

The explicit [live probe](../tools/github-reconciliation/probe.mjs) takes an owned test issue identity JSON and separate `GH_PROBE_REPOSITORY_TOKEN` / `GH_PROBE_PROJECT_TOKEN` variables. `--gh-cli` deliberately selects an already authenticated CLI credential instead; it does not establish minimal permissions. It creates and deletes only a new test Project and journals mutation intent/result outside source. Inspect the journal after an uncertain create/delete before rerunning; a fresh probe must not be used to resolve an unknown earlier mutation. The caller closes its owned test issue separately. Its action/pins are public test fixtures, not an SSH workspace or production installation. See the [receipt and acceptance limits](evidence/W02.3-reconciliation-2026-10-23.md).
